# Архитектура Vault

В этом документе описаны компоненты Vault и фактические потоки запросов.
Инструкции по запуску и вызовам API находятся в [USAGE.md](USAGE.md), краткое
описание и установка — в [README.md](README.md).

## Обзор

Vault — монолитное приложение FastAPI. В одном процессе работают REST-маршруты,
GraphQL API на Ariadne и SSR-интерфейс Jinja2. SQLAlchemy работает с PostgreSQL,
Alembic управляет схемой, Redis хранит blacklist отозванных access-токенов и
краткоживущие данные незавершенного согласия OAuth.

Основные точки сборки: `app/main.py` и `app/config.py`. Веб-маршруты подключены
под `/web`, REST-аутентификация — под `/auth`, OAuth/OIDC — под `/oauth` и
`/.well-known`, GraphQL смонтирован на `/graphql`.

## Компоненты

### Конфигурация и запуск

`app/config.py` читает переменные окружения и `.env`. Для запуска обязательны
`DATABASE_URL`, `PASSWORD_PEPPER` (не короче 32 символов) и `SESSION_SECRET`
(не короче 32 символов). Дополнительные параметры имеют значения по умолчанию:

| Параметр | Назначение |
|---|---|
| `REDIS_URL` | Redis; по умолчанию `redis://localhost:6379/0` |
| `ISSUER` | Издатель JWT и OIDC; по умолчанию `http://127.0.0.1:8000` |
| `RSA_KEY_PATH` | Путь к приватному PEM-ключу; по умолчанию `./keys/rsa_private.pem` |
| `RSA_KEY_ID` | Идентификатор публикуемого ключа |
| `ACCESS_TOKEN_TTL_SEC` | Срок жизни access-токена, по умолчанию 900 секунд |
| `REFRESH_TOKEN_TTL_DAYS` | Срок жизни refresh-токена, по умолчанию 30 дней |
| `AUTH_CODE_TTL_SEC` | Срок действия кода авторизации, по умолчанию 60 секунд |
| `PKCE_REQUIRED_FOR_PUBLIC` | Требовать PKCE для публичного клиента |
| `CONSENT_TTL_SEC` | Срок жизни ожидающего согласия, по умолчанию 300 секунд |
| `SESSION_COOKIE_NAME`, `SESSION_TTL_MIN` | Имя и срок веб-cookie |
| `ENVIRONMENT` | При значении `production` включает флаг `Secure` для cookie |

Секреты и ключи не следует хранить в исходном коде или передавать через общие
журналы. Пример заполнения `.env` с явными заполнителями дан в [README.md](README.md).

### API и веб-слой

- `app/auth/` — REST-регистрация, вход и получение профиля пользователя.
- `app/graphql/` — GraphQL-схема и разрешители; административные операции
  защищены директивой администратора.
- `app/oauth/` — OAuth endpoints, аутентификация клиента, grant-обработчики,
  токены, Discovery, JWKS, UserInfo, отзыв и интроспекция.
- `app/web/` — SSR-маршруты, формы, CSRF-проверки, аккаунт, консоль администратора
  и consent screen.
- `app/audit/` — запись событий в аудит.

### Модели и хранилища

- `User` хранит учётную запись и административный статус.
- `OAuthClient` хранит идентификатор клиента, хэш секрета конфиденциального
  клиента, разрешённые URI перенаправления, scopes и grant types.
- `AuthCode` хранит хэш одноразового кода авторизации, URI перенаправления,
  scope и параметры PKCE.
- `RefreshToken` хранит хэш токена, семейство, сроки действия и состояние
  использования/отзыва.
- `UserSession` отражает OAuth-сессию, связанную с семейством refresh-токенов.
- `WebSession` — серверная веб-сессия пользователя; cookie содержит
  подписанный идентификатор сессии.
- `AuditEvent` хранит события безопасности и административные события.

Схема базы данных задаётся моделями и миграциями в `alembic/versions/`.
Веб-сессии и OAuth-сессии — разные механизмы: отзыв веб-сессии сам по себе не
является отзывом OAuth-токена.

## Поток входа через браузер

1. Клиент направляет браузер на `GET /oauth/authorize` с параметрами
   `response_type=code`, `client_id`, зарегистрированным `redirect_uri`, `scope`,
   `state` и (для PKCE) `code_challenge`/`code_challenge_method`.
2. Endpoint проверяет веб-сессию. Если пользователь не вошёл, браузер
   перенаправляется на `/web/login` с возвратом к исходному запросу.
3. Проверяются активность клиента, точное совпадение `redirect_uri`, допустимые
   scopes и grant type; публичному клиенту требуется PKCE S256.
4. Параметры запроса временно помещаются в Redis. Пользователь попадает на
   `/web/consent` и подтверждает или отклоняет выдачу доступа.
5. При подтверждении создаётся одноразовый код с ограниченным сроком действия.
   Браузер перенаправляется на зарегистрированный callback с `code` и `state`.
6. Клиент отправляет код на `POST /oauth/token`, передавая исходные
   `redirect_uri` и `code_verifier`. Для конфиденциального клиента дополнительно
   проверяется `client_secret` (в теле запроса или HTTP Basic).
7. После проверок код помечается использованным. Выдаются access-токен,
   refresh-токен и, если запрошен scope `openid`, ID-токен.

Если пользователь отказал, клиент получает `access_denied` и исходный `state`.
Если `redirect_uri` недействителен, перенаправление на него не выполняется.

## Токены и меры защиты

- Access- и ID-токены подписываются RS256. Публичный ключ публикуется через
  `/.well-known/jwks.json`; Discovery доступен на
  `/.well-known/openid-configuration`.
- Одноразовые коды хранятся в базе в виде SHA-256-хэша. Повторное использование
  кода отклоняется.
- Для публичного клиента при включённом `PKCE_REQUIRED_FOR_PUBLIC` требуется
  `code_challenge_method=S256`; проверка выполняется при обмене кода.
- `client_secret` конфиденциального клиента хранится в виде Argon2id-хэша и
  показывается только при создании/ротации. Публичный клиент не имеет секрета.
- Refresh-токены ротируются при успешном обмене. Повторное использование уже
  использованного токена приводит к отзыву семейства токенов и связанной
  OAuth-сессии.
- При отзыве access-токена его `jti` вносится в Redis blacklist до истечения
  токена. Проверки защищённых endpoint учитывают этот blacklist.
- Веб-сессия хранится на сервере в таблице `web_sessions`; cookie подписывается
  Starlette `SessionMiddleware`, помечается `HttpOnly` и `SameSite=Lax`.
  Для форм веб-интерфейса используется CSRF-проверка. В `production` включается
  атрибут `Secure`.
- Аудит регистрирует ключевые OAuth-события, входы, операции с клиентами и
  сессиями. Секреты и значения токенов не следует помещать в metadata аудита.

OAuth endpoint'ы используют Bearer-токен там, где он нужен для доступа к
пользовательским данным, например `GET /oauth/userinfo`. Авторизационный endpoint
использует cookie веб-сессии, а не Bearer-токен.

## Реализованные endpoint'ы и ограничения

Поддерживаются `authorization_code`, `refresh_token`, `password` и
`client_credentials`. Для OIDC доступны Discovery, JWKS, ID-токены и UserInfo.
Поддерживаемые scopes: `openid`, `profile`, `email`, `offline_access`.

`password` оставлен для учебной совместимости и считается устаревшим; для новых
интеграций используйте Authorization Code с PKCE. `client_credentials` доступен
только конфиденциальным клиентам и не представляет пользователя.
